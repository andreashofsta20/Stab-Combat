# Gameplay reliability review — 2026-10-03

This pass preserves the knife's existing tap/hold controls, linear charge curve, straight path and balance. The source was reviewed against Roblox's official documentation and verified with deterministic regression tests. Native rendering, mobile safe areas, animation permissions and live replication still require the Studio checks below.

## Changes

- **Keybinds:** the Stab binding now actually controls knife input. Either configured knife input retains tap-to-stab / hold-to-throw. Mouse buttons 1–3 work for Stab and ThrowKnife; movement/emote/slots require keyboard bindings. Unknown keys, controller-only inputs, duplicates and reserved engine keys are rejected. R remains reserved for revolver reload. Existing invalid saved bindings are repaired on hydration. Releases processed by menus still end the original held input; rebinding, focus loss, chat and menus cancel it. Keyboard-equipped touch devices can open the editor.
- **Daily rewards:** kept the 14 rewards, rolling 24-hour eligibility and non-resetting streak. Status requests and claims have separate limits. A failed item grant cannot pay XP or consume the claim. Inventory, balance, claim time and streak are captured together through ProfileManager. UI rows are reused; emote previews stop when the panel closes. Countdown deadlines use elapsed time, with one-second visible updates.
- **Quests:** preserved the pool, daily deterministic selection and UTC reset. Progress and claimed flags now live in `Profile.Data.DailyQuests`, alongside Cash. ProfileStore owns saving and session shutdown; quest progress no longer writes another DataStore every few seconds. Changes coalesce into one client update and UI rows update in place. Elapsed playtime includes fractional seconds. Failed legacy reads remain unavailable and retry, with same-day gameplay progress buffered meanwhile.
- **Hover:** the white outline follows the player's body silhouette. One disabled local Highlight is prepared per remote character at spawn, with a stable Adornee. Hover switches only Enabled, displaying at most one; it creates no instances, retargets no highlights and allocates no listeners. Menu children and character ownership are cached, and raycast parameters are reused. Selection checks run on Heartbeat at 15 Hz with no work between checks. The old hover GUI stays hidden, with no thumbnails/tweens/profile work. No profile remote is looked up or fired until a confirmed desktop double-click or world double-tap. Character replacement and leaving destroy the old highlight/listeners. Native Highlight rendering has a GPU cost; actual live FPS still requires Studio profiling.
- **Lobby map:** Cargo Port is cloned at startup and restored after each round. The preview is excluded from participant spawn/respawn resolution; its embedded scripts and SpawnLocations are disabled. A validated round map replaces the preview, including when Cargo Port itself wins. There is one tracked gameplay map; permanent IntermissionMap stays intact.
- **Knife:** client/server tuning comes from KnifeConfig. The old server loop swept a straight path in up to 120 raycasts without yielding; one equivalent ray now resolves it at the same immediate hit timing. Damage stays server-authoritative. Client cosmetics are anchored and nonqueryable, capped, reconciled to the confirmed impact, and cleaned up. Duplicate server cosmetics and unused per-stab animation loads were removed. Acknowledgement no longer teleports the visible knife to its impact. Foreground behind the player's firing plane cannot flip the aim direction. Overlapping throws cannot permanently hide the hand tool.
- **Mobile:** the THROW button owns its touch until release, even outside the button. Camera/joystick drags cannot charge or release someone else's gesture. Tap in the world stabs with a knife or shoots with a revolver; processed UI taps do neither. THROW targets the center dot. Existing revolver SHOOT/RELOAD/AIM controls and native Roblox jump remain. PreferredInput changes switch the mobile frame without assuming every touch-capable PC is a phone.
- **Animations:** a server script ensures each Humanoid has a replicated Animator. Movement and knife clients use that Animator. The movement script is scoped to one character and cleans up old bindings/connections/tracks. Walk/run/crouch priorities and looping are explicit. It starts idle immediately, checks the selected track every 0.25 seconds, restarts a stopped track and makes bounded retries/fallbacks for unloaded custom assets. Movement waits for Animator replication instead of quitting after five seconds.

See [Weapon effects and round music](WEAPON_CONFIGS.md) for the follow-up changes: 500–750 stud/sec knives, white defaults/Frostbite colors, per-skin revolver effects, ongoing-game music, and round/kill lifecycle fixes.

## Reported cursor, aiming, placement and leaderboard bugs

The mobile shift-lock image starts hidden, follows the actual toggle and resets on death/character removal. The legacy mobile crosshair stays hidden. Revolver HUD/crosshair start hidden, clear immediately on unequip/removal, and cannot reacquire a character being removed. Weapon images are GUI-only; the weapon script never overwrites or restores Mouse.Icon. Roblox's native shift-lock controller can therefore preserve its own unlocked cursor while weapons are equipped, without the overlay contaminating its saved cursor.

The knife and revolver share the requested crosshair image below their retained white dot. `MouseCursorVisibility` coordinates the overlay and ADS: releasing either one cannot restore the native pointer while the other still needs it hidden. Unequip, menus and character cleanup release ownership, restoring the initial native visibility after the final owner releases it. Hover remains entirely local until double-click; prepared highlights preserve the requested body outline and remove hover-time creation/retargeting. Disabled highlights consume engine slots but no rendering cost; the cache is bounded by current remote players and cleans up on character/player removal. The first visible native highlight still incurs the engine's GPU rendering cost.

The support-arm solver previously changed its up vector abruptly near vertical angles. It now uses a continuous shortest-arc rotation. Very close floor/wall hits have a minimum cosmetic aiming distance, body turning blends out near vertical angles, and camera shoulder suppression has separate enter/exit distances to avoid collision jitter. Shot raycasts, damage, range and recoil balance are unchanged.

Map placement accepts invisible/nonqueryable spawn markers. Ready profiles wanting the round are included even while their characters are loading. A shared eight-second retry window waits for healthy characters/roots, clears residual velocity and checks root position after teleport. Players stay anchored during the fight countdown. Verification repairs displacement or character replacement, and combat starts only after every remaining eligible participant is confirmed. Failed placement aborts the round even when other players meet the minimum. All anchors are restored on start, abort or map replacement. SpawnLocations inside gameplay maps are disabled so native automatic respawns cannot bypass the controller. Streaming-enabled games request the destination before confirmation; a failed request cannot confirm placement. These checks verify server placement, not an absolute guarantee of client content loading.

Map replacement validates and prepares the next clone outside Workspace, removes the old map, waits at least `MapSwitchDelaySeconds` (currently three seconds), then publishes the new clone. This applies to gameplay/lobby replacements and separate remove/add calls; the initial map can appear immediately when nothing was removed. A version guard cancels pending publication after a newer valid request or cleanup, so overlapping calls cannot restore an obsolete map or create duplicates. Stray maps appearing during the pause are removed and start a fresh interval. Placement/respawn cannot resolve a map during the gap, and MainGame waits for Spawn to finish before its existing post-load settling/placement steps. The pause separates server deletion/publication; it does not prove every client has replicated the new geometry.

Every round participant receives a visible `RoundStartProtection` ForceField immediately before movement is released and combat becomes active. It lasts 1.5 seconds from that transition, rather than consuming its duration during the countdown. Revolver, stab and thrown-knife damage already respect ForceFields, so protected hits produce no damage or kill credit. Lobby spectators receive no shield. Timers own the exact created instance; cleanup removes only round-owned fields, and old timers cannot remove a later round's shield. OnJoined's one-second cleanup targets only Roblox's default field named `ForceField`, preserving the round-start field on a recently replaced character. This setting applies to round starts in both modes; FFA respawn protection is unchanged.

Profile and legacy names are preserved in `DataConfig`. Levels/kills/gold ordered stores now use `DataConfig.GetLeaderboardScope()`, derived from `ProfileStoreName` plus `LeaderboardVersion`. Old global-scope top players are excluded immediately, without deleting their old entries or modifying player profiles. The new boards repopulate from current hydrated players as they join. Future profile store renames belong in this shared config; increment `LeaderboardVersion` for an intentional board reset within the same profile namespace. Restart servers to activate a new scope.

Leaderboard listeners wait for hydration, cached live values are merged after yielding store reads, and failed reads preserve the current cache. The client subscribes before its initial request, clears old Studio rows, reuses unchanged rows and fetches portraits asynchronously through a four-request queue shared across boards. Updating a kill/cash value no longer destroys every row or repeats every portrait request.

## Startup loading and failures

The reported client console showed multiple systems waiting indefinitely for `leaderstats`. OnJoined previously subscribed to PlayerAdded only after requiring the round/map modules. Map startup can yield while removing Studio leftovers and waiting to publish the lobby preview; a player joining in that interval had no setup callback and was never backfilled. The configurable delay exposed an existing listener race rather than a syntax error in the settings.

OnJoined subscribes before taking a current-player snapshot and initializes both new and already-connected players. Each player is claimed before any yielding setup to prevent duplicate scaffolding/profile loads. MainGame is resolved inside separate character tasks, so map publication no longer blocks profile hydration. Inventory is resolved only when granting the starter item. Existing and future characters receive the same death/reset hooks, with duplicate/stale-character guards. Default spawn-field cleanup preserves the separate round-start shield. Unexpected hydration errors leave DataReady false, release the session and disconnect the affected player rather than exposing incomplete data. Session loss also clears readiness; a yielding VIP lookup cannot mark an inactive session ready. The current three-second map delay and one-second knife throw cooldown are preserved.

Server bootstraps and the client controller bootstrap now use StartupLoader. One shared queue per VM launches at most two jobs between frame yields. Each require/Init runs independently under protected execution; a blocked or failed job cannot prevent later jobs from starting. A group/Init hook is registered once. Loader records distinguish queued, loading, ready and failed jobs, include elapsed duration, and expose counts on the bootstrap instance. A slow-module warning is diagnostic only: it does not cancel legitimate loading or replace saved player data. This limits the number of launches per frame; individual module work and native asset decoding can still take longer than a frame budget.

StartupService publishes ServerReady only after all configured core server groups finish successfully. GameLoop waits for this event before entering intermission/voting, replacing StartServer's ten-second pause and the additional two-second delay. Failed core jobs keep gameplay unavailable and identify the failing group/module; an optional admin failure does not block gameplay. Required map templates, weapon containers, ProfileStore package and tutorial remotes use bounded, validated asset resolution instead of indefinite waits. Other modules still use Roblox replication waits where appropriate; the loader identifies slow jobs without claiming every asset/network operation is bounded. Repair a missing asset/module and restart the playtest; erroring ModuleScripts are not repeatedly retried with duplicate side effects.

ProfileManager no longer depends on tutorial remotes. TutorialService owns onboarding, and the client requests it once only after its profile and server are ready. VIP status waits for hydration and catches existing players, avoiding a competing pre-hydration refresh. Admin panels also catch existing authorized players without duplicate clones. Hitbox initialization subscribes before backfilling, is idempotent, and rejects roots arriving for an old character. The client now explicitly starts status, countdown, zone and overhead controllers; HitFeedback and HandleGameUI no longer block the remaining controller launch loop.

Game status is stored in ReplicatedStorage.GameStatus for late clients. Repeating an unchanged waiting message produces no extra remote events. The status client subscribes before waiting for UI and retains the latest status until its label appears. Failed server startup displays a clear unavailable message rather than pretending the server is ready.

RewardStand binds rewards and quests without waiting for lobby geometry. It watches the lobby path and the selected stand, attaches an existing or arriving trigger, disconnects streamed-out/replaced parts and cleans listeners when the frame is destroyed. It prefers a BasePart named Touch directly or anywhere under the stand, then accepts the stand itself when it is a BasePart. It never guesses an arbitrary decoration as the trigger. Initial overlap handles a player already on a newly replicated pad. One cached overlap filter is updated on character replacement, with no idle overlap queries. Close buttons and refresh/readiness subscriptions finish even while the pad is missing. In Studio, models at IntermissionMap.1_Selection and 2_Selection still need a valid Touch part; permanently deleted geometry cannot be reconstructed from this source-only project.

For diagnostics, inspect ReplicatedStorage's ServerStartupState, ServerStartupPending and ServerStartupFailures, the server/client bootstrap's StartupState/StartupLoaded/StartupTotal/StartupFailed, and each player's DataReady/DataLoadState. These report script/profile readiness, not proof that every client has rendered geometry or decoded every sound/animation.

## Quest migration and rollout

The original `DailyQuestsProgress_v1.0` store is read only. Once a player's session-locked profile and leaderstats are ready, a successful read imports same-day progress/claimed flags into `DailyQuests`, marks `MigrationComplete = true`, and queues a profile save. A failed/corrupt read neither marks migration complete nor writes blank defaults. A migrated profile skips subsequent legacy reads. Cash and quest claim flags are serialized in the same profile snapshot, removing the former cross-store partial-claim path.

ProfileStore saves are asynchronous; a queued save does not prove durable persistence. Autosave/session shutdown still matter. Existing DataStore names were preserved, and this source change did not edit production records. For rollout, use a staging copy first, keep backups, and replace/restart servers running the old quest writer together. A rollback to the old quest script alone would ignore claims now stored in DailyQuests and needs reconciliation.
